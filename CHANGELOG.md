# Changelog

## Unreleased

### After upgrading

- A scan or link that finishes with a file it could not read, hash or link now exits with code 2, where it exited 0, a link run stopped partway by Ctrl+C, SIGTERM or the dashboard's cancel exits 1, and a command line DejaView cannot read, such as an unknown option, exits 1 where it exited 2. A cron line that alerts on any non-zero code now alerts on those runs; the report and the log say which file failed and why. [#5]
- `total_saved_bytes` in a link run's report is what the run freed, where it was every planned path's size, failed ones included; in a scan's it counts a cross-seeded download once. `planned_bytes` and `freed_bytes` give both. [#5]
- Files whose names are not valid UTF-8 are hashed once more on the first run, since their cache entries are now keyed by their exact bytes; every other entry is kept as it is. [#5]
- A link run that planned nothing leaves `.dejaview_link_report.json` as it was, so it keeps the last run that did something. Before, every link run overwrote it, with an empty report when there was nothing to do. A path given with `--report` is still always written. [#5]
- A scan, link or `cache cleanup-temp` that finds another run going exits with code 3 and changes nothing. A cron line that alerts on any non-zero code should treat 3 as nothing to report; the README's cron example does. [#3]
- A report entry's `status` can now also be `already-linked` (the download already was the library file, so nothing changed; such pairs used to be reported as `applied`) or `skipped` (left alone on purpose, with the reason in `error`). A script that counts statuses should know both. [#3]
- A pair that mergerfs's `link-exdev` option turned into a symlink is reported with `method` `symlink`, where it used to say `hardlink`. [#3]
- Building DejaView needs Rust 1.89 or newer. [#3]
- Files under 1 MiB are now skipped by default, so `.nfo` files, text subtitles and artwork are no longer linked. Set `dejaview config set-min-size 1` to link small files again. [#3]
- `threads` now sets how many files are walked and quick-hashed at once, 16 when unset, where it was every hash's thread count and the number of CPUs when unset. Full reads have their own `full_threads`, 2 when unset; set it to 1 for a single spinning disk. [#4]
- The cache file changes form on the first run: each entry is keyed by its folder and its path below it, and may hold a quick hash only. The change hashes nothing again, but a version older than this one reads the new cache as unusable and hashes every candidate again. [#4]
- Walks now leave out the folders a NAS or an OS keeps for itself: `@eaDir`, `#recycle`, `#snapshot`, `@Recycle`, `.@__thumb`, `.recycle`, `.snapshots`, `.Trash-*`, `$RECYCLE.BIN` and `lost+found`. A file in one of them is no longer linked, nor used as the library file a download links to. `dejaview config set-exclude` changes the list, and with no pattern leaves nothing out. [#4]

### Added

- `--quiet` (`-q`) on `scan` and `link` prints nothing unless the run linked something or something failed, so a cron job mails only when something happened. The README's cron example uses it. [#5]
- The report says how its run ended (`outcome`: `complete`, `cancelled` or `failed`), when (`started_at`, `finished_at`), with what (`version`, `downloads`, `media`, `link_mode`), how many downloads became symlinks (`symlinked`) and how many pairs already were one file (`already_linked`, `already_linked_bytes`). [#5]
- `dejaview config set-full-threads N` sets how many files are read in full at once. [#4]
- `dejaview config set-exclude [PATTERN]...` sets the file and folder names every walk leaves out, as globs, with everything under them. The report counts what the list left out in `skipped_by_exclude`, the summary says how many, and the log names each. [#4]
- `DEJAVIEW_CONFIG` sets the config file's path and `DEJAVIEW_LOG` the log's, or `-` for stderr, for containers and services run as a user with no home folder. [#3]
- `dejaview config validate` tries one real hardlink from the library into downloads and says whether link runs will make hardlinks, and if not, why: different filesystems or mounts, or ownership and `fs.protected_hardlinks`. [#3]
- Scans and links list symlinks in downloads that point into the library and no longer resolve, on stderr and in the report's `dangling_symlinks`. [#3]
- A link run's summary says how many downloads became symlinks. [#3]
- `dejaview config set-min-size BYTES` and `--min-size BYTES` on `scan` and `link` set the smallest file a run considers, and the report counts what the floor skipped in `skipped_by_min_size`. [#3]

### Changed

- `scan` and `link` print the downloads and media folders once and each path below its folder, with a size column, where every row repeated both absolute paths. A link run ends with one line saying what it did, such as `Linked 7 of 8, 8.0 MiB freed, 1 failed: see <report>`, naming any downloads that became symlinks, and a run that finds nothing says `No duplicates found.` over no table. Before, a run with failed links still ended with "Potential space saved" and "Done", and none said how much space it freed. Sizes are in KiB, MiB and GiB. [#5]
- A scan or link run from the dashboard reports which file it is on and how many it has found or hashed up to ten times a second, instead of once for every file, which on a large library sent the dashboard hundreds of thousands of updates. [#4]
- Hashing makes fewer round trips to a network drive: quick and full hashes read exactly the bytes they hash, where each spent one or two more reads finding the end of the file, and a full hash reads 8 MiB at a time instead of 1 MiB. [#4]
- Linking makes fewer round trips to a network drive: each link looks up the library file once, where it looked it up four times, and the download once instead of twice. [#4]
- In the dashboard, `l` and `L` link the reviewed rows without walking both folders again when neither file of any row has changed since the scan hashed it; a row that changed sends the run back to the walk, which checks every row as before, and so does a download that has other hardlinks or that the cache knows as a library file seen through a second mount. Such a run's report counts only the rows' files in `files_considered`. Before, every link from the dashboard walked both folders first, which takes minutes on a network drive. [#4]
- The same share mounted at two paths, such as in a Docker cron job and on the host the dashboard runs on, now uses one set of cache entries. Before, each run pruned the other's entries as gone and the next one hashed them again. [#4]
- A run that learns nothing new leaves the cache file as it is. Before, every run rewrote and flushed it, tens of megabytes on a large library. [#4]
- Downloads and media are walked at once, many folders in parallel, so a run on a network drive no longer waits on one `stat` after another before hashing starts. [#4]
- A repeat scan reads only files it has not hashed before: the cache now keeps each file's quick hash too, so a file whose quick hash matched no other is not read again. Before, every file sharing its size with a new or changed one was read again on every run. [#4]
- A file of 1 MiB or less is read once, not twice: its quick hash reads it whole and stands as its full hash. [#4]
- Files of a size that no download shares with a library file are no longer read, nor are those where every download already is a library file: no link can come of them. [#4]
- The dashboard's logo is "déjàview" in lowercase pixel letters with depth, teal with two orange accents, and shows whenever the full header does, from 100 columns. Before, it was block capitals, and below 119 columns the header showed the name as plain text instead. `dejaview tui-logo-preview` shows the logo on its own.
- The dashboard shows each download beside its library file with the link between them drawn in the middle: a green line for a hardlink, an amber arrow for a symlink, a dashed orange line for a pair not linked yet, a red ✗ for a failure. A season's episodes sit under their release folder, the space to free (or freed) is drawn big above them with the count of each kind of link, and the selected pair is told in full below, with why it is a symlink or why it failed. While a scan runs it shows its steps and the files it reads. The keys at the foot are the ones that work on the screen shown, the next step first. Before, every row showed the same "PLANNED" and "TRY HARDLINK" chips, a symlink wore the same APPLIED chip as a hardlink, told apart by a lighter shade and the OUTCOME column, which a narrow terminal hid, the counts were repeated in four places, and a running scan's results pane said no duplicates were loaded. The settings the sidebar listed are in Help.
- Saving the folders in the dashboard's path editor tries one hardlink between them, as `dejaview config validate` does, and the dashboard says whether link runs will make hardlinks or symlinks, and why.

### Fixed

- A file whose name is not valid UTF-8 can be linked from the dashboard, and two names that differ only in such bytes are told apart: a report entry gives such a path's bytes in hex in `source_raw` or `target_raw`, and the cache keys each name apart. Before, `l` and `L` linked nothing for such a file, its report rows could not be told apart, and the cache kept one entry for both names, so both were hashed again on every run. [#5]
- `cache audit-temp` and `cache cleanup-temp` find a temporary symlink left beside a download by a run stopped partway, and remove the link without touching the library file it points at. Before, they listed and removed only temporary files. [#5]
- A folder DejaView cannot read, such as a NAS's recycle bin, no longer stops the cache from forgetting files that are gone: entries under that folder are kept and the rest are dropped as usual. Before, one unreadable folder kept every stale entry for good. The log now names each path a walk could not read, and why. [#5]
- Verifying large files shows progress in bytes, with the speed and the time left, in the dashboard (`12.3 GiB of 40.0 GiB  |  150.0 MiB/s  |  ETA 03:05`) and on the CLI's progress bar. Before, both counted whole files, so a 60 GB remux sat at "0 / 8" for minutes, and a read that failed or that a cancel stopped was counted as verified. [#5]
- `config set-downloads` and `config set-media` name the path they could not use, where they said only "No such file or directory". The dashboard's path editor reads `~` as the home folder, says which field an error is about, shows a long error whole, and names the config file it saves to. [#5]
- In the dashboard, `x` and `X` ask before clearing the cache, which means reading every file again. Before, `x`, next to `c` and in no list of keys, cleared it at once. [#5]
- In the dashboard, the selected row carries a marker, `PgUp`, `PgDn`, `g`, `G`, `Home` and `End` move through the rows, and Help and the JSON preview scroll with the same keys, so a report of hundreds of entries can be read to its end; `j` no longer closes the preview. After `l` links a row, the selection moves to the next planned row instead of back to the first. [#5]
- The dashboard fits an 80x24 terminal, and works down to 60x20: below 30 rows or 100 columns the header gives up the logo for three lines of counts, below 96 columns the rows leave the library file to the details under them, the dialogs are as tall as their text, and the footer always keeps `? help`. Before, at 80x24 the dialogs cut off their own prompt, Help stopped halfway and the Run Log had one line; at 60x20 the footer and the log disappeared. [#5]
- The dashboard's rows can be told apart: each shows its download below the downloads folder, cut so the file name stays, with its size, and on a wide terminal the library file too. Before, every row showed the same start of its absolute path, so a season's episodes looked alike and, at 60 columns, showed only `/`. `p` switches the table between these and full paths. [#5]
- The dashboard's log keeps to what a person needs to read: progress counts ("Collected 25 file(s)", "Hashing files: 10 / 40", "Applied 3 / 8") stay in the header, which no longer names a file the run has moved past. Scanning before the paths are set opens the path editor, where it used to fail with "downloads path not set". [#5]
- In the dashboard, a scan or link that fails, from a missing path to `--strict` stopping on a file it could not read, shows its error in one line, and a link `--strict` stopped partway shows which rows it linked and which failed. Before, a failure while hashing showed the run's raw error output, a backtrace included, and a link stopped partway left every row planned. [#5]
- A dashboard left open while DejaView is upgraded keeps working: it runs scans and links with the binary it was started from, and refuses, asking to be restarted, a binary that speaks another version of its event stream. Before, once the binary was replaced on disk, every run failed. [#5]
- A failed pair's `error` in the report keeps the OS error, such as "Read-only file system", where it said only which step failed, and its `method` and `fallback_reason` no longer claim the planned hardlink. [#5]
- `--json --strict` prints the report before stopping on a failure, and a path given with `--report` is written, whether the failure came while walking, hashing or linking; a run stopped before it planned anything reports outcome `failed` with no entries. Before, it printed nothing on stdout and wrote no report. [#5]
- Planned pairs come in download path order in the table, the report, `--json` and the dashboard. Before, the order changed on every run, so two reports could not be compared, and the dashboard's rows reshuffled when a scan finished. [#5]
- Ctrl+C, SIGTERM (a cron timeout, `docker stop`) or SIGHUP stops a scan or link before its next file and keeps the hashes it finished; a second Ctrl+C stops at once. Before, it ended the process on the spot and every hash of the run was lost, so a first run over a network drive that was interrupted started over from nothing. A run started under `nohup` still ignores hang-ups. [#4]
- While hashing, the cache is saved every five minutes, so a run killed outright (SIGKILL, a power cut, a container stopped without grace) loses at most that much hashing. Before, it was saved only once hashing ended. [#4]
- A cache file that cannot be read or parsed is named in the log with the reason before DejaView starts over with an empty one. Before, it was replaced silently, and the next run hashed the whole library again with no explanation. [#4]
- The dashboard's log shows its newest lines, and the header says how the last run ended. Before, the log stayed on its first few lines, so "Scan finished", a failed link and the reason for it (such as another run holding the lock) showed nowhere. The link confirmations show `y link` and `n cancel` on their border, so a small terminal no longer cuts the prompt off. [#3]
- Only one scan, link or `cache cleanup-temp` runs at a time per downloads folder. Before, two link runs failed each other's pairs, the later one overwrote the other's report and cache, and `cache cleanup-temp` could delete a link another run was about to rename into place. [#3]
- A download that already is its library file is reported as `already-linked` and counted apart from applied pairs. On mergerfs without `use_ino` or `inodecalc=hybrid-hash`, which gives one file two inode numbers, such pairs were reported as applied on every run. [#3]
- In the dashboard, `L` links only the planned rows the last scan showed, each to the library file it showed, and does nothing before a scan has finished; `l` likewise links its row only to the library file shown. Before, `L` ran a fresh link over everything, including duplicates that appeared after the scan and, before any scan, all of them. The confirmation counts rows with errors only. [#3]
- A log that cannot be written no longer stops every command: DejaView warns once, naming the path, and runs without it. Before, an unwritable state folder failed even `config show`, with an error that named no path. [#3]
- A run whose downloads folder reaches the library through a bind mount, or the reverse, stops before changing anything, and `config validate` reports it. Before, only paths were compared, so a library mounted inside downloads was walked as downloads and its files were rewritten. [#3]
- A download already hardlinked to one library copy is left alone when the library holds a second identical copy. Before, it was relinked to the copy whose path sorted first, which broke the hardlink Sonarr or Radarr made and freed nothing. [#3]
- A download that is a library file seen through a second mount (a bind mount, or a mergerfs branch while media points at the pool) is left alone, and the run warns and counts it in the report's `skipped_as_library_file`. Before, such a file could be replaced by a link to itself or to another copy, destroying the library's only copy. [#3]
- Downloads that are hardlinks of each other, as cross-seeding makes, are all linked in one run. Before, replacing the first path failed every other one with "source changed since planning", and a `--strict` run stopped there each time. [#3]
- A pair is left alone, with status `skipped` and the reason in the report, when linking would leave the download unreadable to its owner or group; the run, `--strict` included, carries on with the rest. Before, a hardlink handed the download the library file's owner and mode, and a torrent client locked out of its own file stopped seeding. [#3]
- A pair that fell back to a symlink has a `fallback_reason` naming the cause and the OS error. Before, it said only which command failed. [#3]
- On Linux, a download is replaced through its folder opened once, and both the new link and the download are checked against the plan right before the rename, so a folder or library path swapped during a run cannot redirect the replacement, and a library file replaced mid-run fails the pair instead of being linked. A download whose folder resolves outside the downloads folder is refused. [#3]
- Empty files are never linked. Before, every empty download was linked to an empty library file, and a torrent client that later wrote into a freshly created file wrote into the library. [#3]
